# PAGE Editor 0.7.0 版本计划与路线图

日期：2026-10-27（UTC+8）  
本次版本：**0.7.0 — 项目与扩展**  
下一功能版本：**0.8.0 — 完整创作交互**

## 1. 最终开发目标

开发基于 Godot 的独立桌面程序 PAGE Editor。直接运行 Windows 或 Linux 发布程序，完成 Dialogic 内容创作、资源管理和运行预览，无须打开 Godot 编辑器运行 PAGE Editor。

1.0.0 必须实现 **Dialogic 2.0-alpha-20 的全部功能**，包括事件及全部属性、运行子系统、创作面板、项目设置、资源管理与自定义扩展，生成与指定版本完全一致标准的代码、配置、资源和内容文件。部分事件、文件可打开或按钮可见不能代替完整目标。

固定依赖为 **Godot 4.7.1 / Dialogic 2.0-alpha-20**。界面基于已验证的 **dialogic_editor_ui_260903.zip**，保持整体场景、布局和主题，按功能局部调整。本对话不维护 MCP 开发。

## 2. 0.7.0 范围与完成条件

本版以已交付的正式 0.6.0 Source 为基础，实现目标项目配置、资源身份/UID/引用、改名事务、原生源码编辑、Signal / Call 和宿主单例、自定义事件/子系统/编辑器/立绘/动画/布局，以及独立目标预览和原生工程移交。无需 0.0.1—0.0.3 的工程文件。

固定引擎、插件、原始 UI 布局及主题保持；原生扩展代码在独立目标进程执行。运行兼容的 DialogicEditor 可打开并执行其保存操作；依赖 Godot 编辑器专属接口的插件继续在固定 Godot 编辑器中使用。

原始完整设计 TC-0.7.0-r1 共 621 条（共有 601、Linux 10、Windows 10），其中新增 88 条，在工程代码修改前已保存。当前发布修订为 TC-0.7.0-r2，仅订正两处状态词笔误；其余619条定义保持原样，原稿与差异证明保留。每条用例独立记录实际执行与持久化证据，不复用此前版本的通过状态。实际完成与限制见 RELEASE_NOTES.md 及本版独立 Test_Progress。

## 3. 完整版本路线图

各阶段同时提供对应编辑入口、原生读写、所需依赖和运行行为。0.8.0 补齐完整创作交互，不代表此前功能只生成文本而没有可用操作界面。缺少宿主脚本、单例或资源时准确说明，不能模拟成功结果。

## 4. 全部功能的覆盖范围

### 4.1 事件与内部结构

Dialogic 2.0-alpha-20 的有效注册范围为 23 个创作事件，加 1 个内部 EndBranch。

| 功能集合 | 事件或结构 | 主要规划节点 |
|---|---|---|
| 文本与注释 | Text、Comment | 0.0.1 基础；0.0.2 变量引用；0.0.4 文本表达式；0.1.0 条件文本；0.4.0 完整文本属性 |
| 角色 | Character | 0.0.1 基础；0.3.0 扩展；相关表现能力与对应阶段联动 |
| 数据与条件 | Variable、Condition；内部 EndBranch | 0.0.3 字面量赋值；0.0.4 表达式赋值；0.0.5 单层条件与 EndBranch；0.1.0 嵌套条件和完整阶段范围 |
| 选项与流程 | Choice、Label、Jump、Return、End；相应分支结构 | 0.2.0 |
| 文本交互与设置 | Wait、WaitInput、TextInput、Clear、Style、Setting | 0.4.0 |
| 媒体与运行状态 | Background、Audio、Voice、History、Save | 0.5.0 |
| 宿主交互 | Signal、Call | 0.7.0 |

Glossary 包含编辑器和运行能力，属于 0.6.0 的明确范围。其指定版本模块没有注册独立创作事件，因此不将其事件文件擅自列入标准事件集合。

### 4.2 运行子系统与创作工具

需覆盖的 19 个运行子系统为：audio、backgrounds、containers、portraits、choices、animation、expression、input、glossary、history、jump、save、settings、styles、text、text_input、variables、voice、wait。

事件和子系统之外，还必须覆盖：

- 时间线的视觉编辑与文本编辑，以及两种模式之间的一致性。
- 角色、立绘、原生立绘预设、样式、布局和相关资源管理。
- 变量、术语、翻译、引用管理和全部设置面板。
- 自定义场景、脚本、动画、布局、立绘、事件、子系统和编辑器扩展接口。
- 标准文件导入导出、依赖定位、资源身份管理及目标工程移交。

### 4.3 原生标准与功能完成定义

| 方面 | 要求 |
|---|---|
| 原生内容 | .dtl、.dch、样式、布局、翻译、设置及扩展资源采用指定版本的标准格式；.dch 使用 Godot Variant 文本序列化 |
| 内容语义 | 正确处理事件类型、全部属性、顺序、缩进、分支、转义、资源身份与依赖 |
| 创作操作 | 每项功能具有可用的编辑入口；操作能够产生对应的标准内容 |
| 运行行为 | 在具有所需依赖时执行对应行为；缺少依赖或尚未支持时准确说明 |
| 独立程序 | 发布程序可直接运行；Source 用于修改和构建，不能替代可执行程序交付 |
| 功能状态 | 只把实际具备的能力列为已实现；功能数目、按钮数目和文件可加载均不能单独代表完整支持 |


## 5. 关键约束

- 不升级固定引擎和插件版本；开发核对官网文档与固定源码，差异以实际固定版本为准。
- 使用指定 UI 工程，保持整体结构。发布包包含可独立运行程序。
- 原生格式与运行语义一致，不建立私有变量权威配置。目标内容根与应用资源根分离。
- config/branding.cfg 集中管理名称、产物前缀、LOGO、应用图标、稳定用户数据目录；VERSION.txt 管理版本。
- 未保存内容、外部修改、缺失依赖、未知属性和失败写入均保护，不静默删减。
- 计划、实现、构建、测试和交付状态分开；只有用户明确“确认，开始写代码”才按确认范围编写下一版本工程。
- 本次授权范围为 0.7.0；不自动延伸至 0.8.0。中间版本不改变后续里程碑编号。

### 6.2 测试用例与状态

- 每个版本的 Testcases.md 都是该版本独立、完整的全量列表；重复用例也完整保留，不以增量清单或引用其他版本的用例代替。
- Testcases.md 只有三节用例：**共有、Linux专用、Windows专用**。共有用例分别列 Linux 状态、Windows 状态；单平台用例列一个状态。
- 每个状态只能是 **已运行 / 未运行**。本项目中的“已运行”表示该平台本用例全部样本满足预期，并已保存可恢复记录。失败、阻塞、中断、未执行均标为“未运行”。
- 失败记录的实际结果仍如实保存为失败；“视作未运行”不表示删除执行历史。重试通过后追加记录，不能覆盖先前失败证据。
- 用例包括测试目的、前置条件、操作、预期结果和稳定编号；多样本逐一记录，任一样本未通过则整条仍为未运行。
- 先生成并保存本版完整测试用例，再完成工程实现（生成代码），最后进行测试。测试期间调整需求或用例时保存新修订，明确影响范围后重测；不能倒改预期以迎合实际输出。
- P0/P1 仅决定执行顺序；本版范围内的 P1 也需完成，不能用优先级豁免。
- 静态检查、单元验证、无界面运行和 GUI 操作分别记录。命令成功退出不能代替界面行为验证；Linux 上检查 Windows EXE 属性不算 Windows 实机测试。
- 用例数不等于运行次数；平台、样本和重试均分别留痕。不得设置未经确认的性能达标结论。
- 测试设计修订及定义指纹不含运行状态列；另记录每次保存后的完整文件 SHA256。仅更新状态不会使已通过用例失效，修改步骤、样本或预期才触发设计修订和影响评估。

### 6.3 每条测试后的持久化与恢复

顺序为：**执行一个用例/样本 → 保存实际结果和证据 → 确认保存成功 → 更新对应状态及进度 → 再执行下一项**。明确保存失败时暂停推进并处理失败；保存结果不明时先核对既有保存，避免重复写入。不能把只存在对话上下文中的通过算作恢复节点。

独立进度采用可追加的执行记录及当前检查点，至少记录：

| 字段 | 要求 |
|---|---|
| 运行序号 | 全局递增序号；同一用例重试也产生新序号 |
| 用例标识 | 用例编号、样本编号、设计修订/定义指纹及当次完整测试清单 SHA256 |
| 被测对象 | 源码/程序标识与 SHA256、平台、系统、工具链及 GUI/无界面/静态方式 |
| 时间与尝试 | 开始时间、完成时间、时区、尝试次数 |
| 实际结果 | 通过、失败、阻塞或中断；实际输出、预期对比及错误信息 |
| 证据 | 日志、截图或文件比较的保存位置及必要哈希 |
| 当前状态 | 按上述规则映射为已运行或未运行 |
| 后续动作 | 待修问题、重试条件、下一用例或样本 |
| 恢复信息 | 最后完整保存的运行序号、进度修订及保存完成标记 |

故障恢复后先读取最后完整保存的检查点和执行记录，核对版本、源码/程序哈希、用例修订及环境。仅对匹配且证据完整的通过记录恢复“已运行”；未落盘或中断项目重新执行。若修改代码或重建程序，评估影响并使相关通过状态失效，运行必要回归；不能沿用不对应交付二进制的通过结论。

独立测试进度包内的 `TEST_PROGRESS.md`、`EXECUTIONS.json` 和原始证据持续记录实现、构建、逐项测试及最后持久化序号，作为故障恢复节点。这些工作记录不属于产品发布文件，也不进入程序包。

### 6.4 平台政策与发布门槛

- 从本次起，每个版本完成共有用例在 Linux 上的测试、Linux 专用测试、双平台实际导出及可执行的 Windows 包静态检查。
- **Windows 实机测试延后至 1.0.0 交付前统一执行。** 在此之前，Windows 专用用例以及共有用例的 Windows 运行状态保持未运行，并在发布说明中明确延期。无需逐个启动所有历史发布包，但 1.0.0 须覆盖此前积累的全部功能和当前用例。
- 1.0.0 不能仅补测 Windows 专用节；还须在 Windows 实机执行全部共有用例，完成真实启动、文件系统、UI 和原生预览验证。
- Linux 本版范围内的失败或未运行项不能计入完成；若受环境限制无法验证，应明确报告阻碍并保留未运行，不能凭静态阅读宣称通过。Windows 实机延期是明确的既定例外，不扩大为全部测试豁免。
- 最终交付包必须与测试证据的程序版本对应。打包后的文件完整性和运行资源需再次核对；只改变过程文档时不无理由重跑全部功能。
- Release_Notes 记录实际测试摘要及未运行事项；Testcases.md 只更新运行状态，详细结果留在独立进度与证据中。
