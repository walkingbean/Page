# PAGE Editor 交付规则

更新日期：2026-10-24（UTC+8）  
适用范围：PAGE Editor 后续版本的工程开发、构建、测试与交付。  
本文不规定单个功能版本的开发范围；各版本范围以另行确认的版本计划为准。

## 1. 最终目标与基本约束

1. PAGE Editor 是基于 Godot 的独立桌面程序。Windows 和 Linux 发布程序应能直接运行，无须打开 Godot 编辑器运行本产品。
2. 最终目标为完整实现 Dialogic 2.0-alpha-20 的功能，包括事件及全部属性、运行子系统、创作面板、项目设置、资源管理与自定义扩展，并输出符合指定版本原生标准的代码、配置、资源和内容文件。
3. 固定使用 Godot 4.7.1 与 Dialogic 2.0-alpha-20。不得自行升级依赖版本。
4. 界面必须基于已人工验证的 `dialogic_editor_ui_260903.zip`，保持整体场景、布局和主题；可按功能需要进行局部调整。
5. 开发细节须检索 Godot、Dialogic 官方网站和文档，并核对指定版本源码。文档与固定版本实际行为有差异时，应记录差异，以固定版本的实际语义作为兼容依据。
6. 使用 `dialogic2alpha20_godot4.7.1.zip` 所提供的原生验证工程进行适用的功能验证与双向内容比对。
7. 旧版 `TCUA_Dialogic_Standalone_Editor_v0.4.0-issue04-patch2.tar.gz` 仅作参考，不作为可靠开发基础。
8. 本对话不维护 MCP 开发。GitHub 提交、标签和 Release 发布按专门发布通道的授权处理，本交付规则不构成发布授权。
9. 每个版本的实施范围需单独确认。只有用户明确说出 **“确认，开始写代码”**，才按确认后的范围继续生成或修改工程代码。路线图和准备工作不构成后续版本的编码授权。

## 2. 对话中的正式交付文件

每个版本在交付回答中直接提供以下四项文件。下表中的 `{版本号}` 替换为实际版本号。

| 文件名 | 内容与要求 |
|---|---|
| `PAGE_Editor_{版本号}_Source.zip` | 完整可构建 Godot 工程、应用资源、必要依赖、构建工具、示例、文档和许可 |
| `PAGE_Editor_{版本号}_Windows_x86_64.zip` | Windows x86_64 独立程序，以及运行所需资源、说明、示例和许可 |
| `PAGE_Editor_{版本号}_Linux_x86_64.zip` | Linux x86_64 独立程序，以及运行所需资源、说明、示例和许可 |
| `PAGE_Editor_{版本号}_Test_Progress.zip` | 测试执行结果、日志、失败与重跑历史、证据、进度及故障恢复资料 |

具体要求：

- 当前源包内工程根目录按 `PAGE_Editor_v{版本号}/` 命名。
- 当前平台程序分别为 `PAGE_Editor.exe` 和 `PAGE_Editor.x86_64`。
- 发布说明、版本计划与路线图、测试用例不再作为独立文件在交付回答中提供，只随 Source 包交付。
- 测试执行结果压缩包单独提供，并保存至本项目资料库来源；不进入源码仓库的 `docs/`，不随 Source 包或平台程序包交付。
- 每轮问答另附 RECORD 文件。RECORD 不计入上述四项产品交付文件，不进入 Source 包或平台程序包。
- 若之后调整产品名称，相关产物名称按已确认的集中品牌配置统一生成，不在代码中散布名称硬编码。

## 3. 源码文档的位置与维护分工

| 路径 | 内容 | 维护规则 |
|---|---|---|
| `README.md` | 项目宣传主页 | 下一次版本代码交付时由 AI 创建初版；此后由用户手动维护，AI 不自动更新或覆盖 |
| `docs/README.md` | 当前根目录 README 中的使用说明 | 迁入现有 `docs/`，之后随各版本代码交付同步更新 |
| `docs/RELEASE_NOTES.md` | 当前版本的功能、使用边界、实际测试覆盖、未运行事项和已知问题 | 随版本同步更新，只随 Source 包交付 |
| `docs/ROADMAP.md` | 最终目标、完整路线图、版本范围、关键约束和交付标准 | 随版本同步更新，只随 Source 包交付 |
| `docs/TESTCASES.md` | 当前版本独立完整的全量测试用例及运行状态 | 先生成再测试，随 Source 包交付，不单独提供下载 |
| `docs/BUILD.md` | 构建、导出、品牌配置、项目名称与 SVG 替换方法 | 随构建流程和配置变化更新 |
| `docs/DEPENDENCIES.md` | 固定依赖与相关说明 | 随实际依赖情况维护 |
| `docs/OFFICIAL_REFERENCES.md` | 官方文档和指定源码依据 | 随开发核对结果维护 |
| `CHANGELOG.md` | 各版本变更记录 | 在根目录按版本追加、维护 |

补充要求：

1. 使用说明与其他工程文档统一使用现有的 **`docs/`**；不为使用说明另建 `doc/`。
2. `docs/` 中上述文档的文件名使用大写，不附项目名称和版本号。
3. 根目录宣传主页与 `docs/README.md` 分工独立。后续交付应保留用户维护的根目录主页；需要修改时另行取得用户的明确指示。
4. 品牌配置与 SVG 替换的操作方法集中放在 `docs/BUILD.md`，不在根目录或 `docs/` 的 README 中重复保留操作章节；需要时可链接至 BUILD。
5. 迁移文档时同步修正内部链接、构建或打包工具中的文档路径，以及平台使用说明的内容来源。
6. 自动维护的文档应与当版实际功能和边界一致，不将计划能力描述为已经完成的功能。
7. 文档和界面使用 PAGE Editor 的当前产品定位，直接描述功能、目标和版本状态。

## 4. 品牌、版本与源码包要求

1. 项目名称、产物前缀、界面左上角 LOGO SVG、应用图标等使用集中配置；当前配置文件为 `config/branding.cfg`。相关源码、元数据和打包流程读取该配置，避免名称硬编码。
2. 当前版本由 `VERSION.txt` 管理。源码中的版本信息、程序元数据、构建产物名称、变更记录及自动维护的版本文档保持一致。
3. 根目录宣传主页在初版交付后由用户维护，不纳入自动版本文字替换。
4. Source 包须包含修改和构建本工程所需的源码、应用资源、必要插件依赖、工具、示例与许可，并说明外部工具链的取得和使用方法。
5. Source 包不包含 Godot 引擎二进制、导出模板、`.godot` 导入缓存、编译后的平台程序、构建输出、测试执行证据或对话记录。
6. 平台包须包含实际导出的独立可执行程序，不能用 Godot 工程、运行脚本说明或编辑器启动步骤代替。
7. 未保存内容、外部文件修改、缺失依赖、未知属性与写入失败应得到明确处理；不得静默丢失或删减用户内容。
8. 原生内容采用固定 Dialogic 版本的标准格式和语义，不通过私有格式或修改插件语义来掩盖兼容性差异。
9. 未支持或依赖不足的功能必须明确说明；按钮可见、文件可加载或程序成功退出均不能单独作为功能完整实现的依据。

## 5. 全量测试用例规则

### 5.1 用例设计

- 每个版本都提供该版本独立、完整的全量列表；即使与旧版重复，也完整列出，不以增量清单或跨版本引用代替。
- **先生成并保存测试用例，再执行测试。**
- 用例分为三节：**共有、Linux 专用、Windows 专用**。
- 每条用例至少包含稳定编号、测试目的、前置条件、操作步骤和预期结果。
- 共有用例分别设置 Linux 和 Windows 状态；专用用例记录对应平台状态。
- 测试覆盖新增功能、既有功能回归、真实界面操作、独立程序运行、文件与资源操作、原生内容兼容、构建和最终包完整性，并覆盖正常、边界和失败场景。
- 测试期间修改步骤、样本或预期时，保存设计修订，明确影响范围并进行必要重测；不得倒改预期来迎合错误结果。
- 仅更新运行状态不等于修改测试设计；应分别记录用例定义指纹和完整用例文件的 SHA256。

### 5.2 状态含义

每条用例的状态仅使用 **已运行／未运行**：

| 状态 | 判定条件 |
|---|---|
| 已运行 | 该平台该用例全部必要样本满足预期，且结果和恢复证据已经持久化 |
| 未运行 | 未执行、失败、阻塞、中断，或尚有必要样本未完成 |

- 失败的执行在用例状态上视作未运行，但原始执行结果仍如实记录为失败。
- 重跑通过后追加新记录，再更新当前状态；不得覆盖或删除先前失败证据。
- 部分子样本通过，不能代表整条用例完成。
- 用例数量与执行次数分别统计；不同平台、样本及重试分别留痕。
- `docs/TESTCASES.md` 只保存用例定义和运行状态，不写入详细执行结果；详细结果进入独立测试进度包。

### 5.3 真实验证要求

- 静态检查、单元或组件测试、无界面运行、图形界面操作、导出程序运行应分别记录，不能相互冒充。
- 命令返回成功不能代替界面行为验证。
- 原生格式与运行行为的验证应使用指定参考工程完成适用的读取、保存、运行和双向比对。
- Linux 上检查 Windows EXE 属性、资源或文件结构不算 Windows 实机测试。
- 不以优先级降低为由豁免已确认版本范围内的测试；优先级用于安排执行顺序。
- 环境不足时记录实际阻碍和未完成范围，不凭静态阅读宣称通过。
- 不沿用不匹配本版源码或交付二进制的通过结论；修改代码、重建程序后评估影响并进行必要回归。

## 6. 逐项持久化与故障恢复

每项测试的推进顺序为：

**执行用例或样本 → 保存实际结果和证据 → 确认保存成功 → 更新状态及进度 → 执行下一项。**

保存失败时先恢复保存，不把仅存在于对话上下文中的结果作为完成或恢复节点。

每次执行至少记录：

| 字段 | 内容 |
|---|---|
| 执行序号 | 递增编号，重跑产生新编号 |
| 用例身份 | 用例编号、样本编号、设计修订、定义指纹及当次用例文件 SHA256 |
| 被测对象 | 产品版本、源码及程序标识与哈希 |
| 环境与方式 | 操作系统、平台、工具链，以及静态、无界面、GUI 或独立程序等方式 |
| 时间与尝试 | 开始、结束时间、时区和尝试信息 |
| 实际结果 | 通过、失败、阻塞或中断；实际输出与预期差异 |
| 证据 | 日志、截图或文件比较结果的位置及必要哈希 |
| 当前进度 | 对应用例状态、待修问题、重试条件和下一项工作 |
| 恢复标记 | 最后完整保存的执行序号、进度修订和保存完成标记 |

故障恢复时：

1. 读取最后完整持久化的检查点和对应执行记录。
2. 核对产品版本、源码和程序哈希、用例修订及运行环境。
3. 仅对对象匹配且证据完整的成功记录恢复“已运行”状态。
4. 对未完整保存、中断或对象不匹配的项目重新执行或按影响范围重新验证。
5. 保留全部失败、阻塞和重跑历史。
6. 将最终进度、必要证据和恢复说明封装为独立 `Test_Progress.zip`，与交付源码和程序建立可核对的对应关系。

## 7. 平台验证政策

1. 每个版本实际导出 Windows x86_64 与 Linux x86_64 程序，并进行最终包检查。
2. 共有用例在 Linux 上执行，并执行 Linux 专用用例及环境可完成的 Windows 静态检查。
3. **Windows 实机测试延后至 1.0.0 交付前统一完成。** 此前共有用例的 Windows 实机部分及 Windows 专用用例保持未运行。
4. 1.0.0 的 Windows 验证须包括全部共有用例和 Windows 专用用例，覆盖此前积累的全部功能，以及真实启动、文件系统、界面和原生预览。
5. Windows 实机延期不构成其他测试的豁免。
6. Linux 因环境条件不足而无法完成的项目仍标为未运行，发布说明和交付回答如实列明；不能计入通过数量。
7. 已发现但未确定根因的异常应保留日志和复测记录，不能仅因一次重试成功而抹去异常历史。

## 8. 最终构建、打包与校验

1. 用指定引擎和匹配导出模板完成实际构建，记录工具链版本。
2. 核对 Source 的完整性、全新解压后的导入与构建能力，以及平台包的运行资源、说明和许可。
3. 最终交付包必须对应被测源码和程序。代码或程序发生变化时，按影响范围重新验证。
4. 仅调整过程文档且不影响功能时，不无理由重跑全部功能测试；文档路径、内容和打包规则本身仍须验证。
5. 核对压缩包完整性、目录名、文件名、平台类型、版本和必要执行权限。
6. 在最终压缩包字节确定后，计算 Source、Windows、Linux **三包的实际大小与 SHA256**。
7. 三包校验信息直接列在交付回答正文中，由该回答的 RECORD 文件完整记录。
8. 不将 Source 包自身 SHA256 写回包内文档，避免形成循环校验。包内发布说明正常记录功能、边界和测试摘要。
9. 校验后如重新打包或修改任一交付包，重新计算该包的大小和 SHA256，并同步最终回答及其 RECORD。

## 9. 交付回答的内容与 RECORD

每次正式交付回答应包含：

1. 当版版本号、主要完成内容和重要边界。
2. 四项正式交付文件的下载链接。
3. 实际测试覆盖、未运行事项、Windows 实机延期说明，以及影响使用或构建的已知问题。
4. Source、Windows、Linux 三包的校验表，包含：
   - 完整文件名；
   - 文件大小，单位为字节；
   - 从最终文件计算的完整 SHA256。
5. **在正文明确列出该交付回答的 RECORD 文件名，方便复制到发布通道；同时提供 RECORD 下载链接。**

文件名的呈现形式为：

> 交付回答 RECORD 文件名：`YYMMDD-RECORD-HHMM(UTCOffset).md`

实际交付时必须替换为真实文件名，不能保留占位符。上述正文记录与下载链接共同提供，不仅使用“下载记录”等泛称。

RECORD 规则：

- 每轮回答都创建一份 Markdown 记录文件。
- 命名为 `YYMMDD-RECORD-HHMM(UTCOffset).md`，时间及偏移量按用户所在时区确定；当前按 UTC+8。
- 使用一级标题 `# User Input` 和 `# AI Output` 区分用户输入与人工智能输出，两部分之间使用 `---` 分隔。
- 完整、准确记录本轮用户输入和人工智能对外输出，保留 Markdown 表格、列表、强调、代码块、链接等格式。
- 交付回答中的校验表、文件链接和 RECORD 文件名均应完整写入该回答的 RECORD。
- RECORD 随回答单独提供，不写入 Source 包或平台程序包。

## 10. 单个版本的执行顺序

1. 整理并确认版本范围与适用交付规则。
2. 等待用户明确授权“确认，开始写代码”。
3. 核对固定依赖、官方文档和参考工程，生成并保存完整测试用例。
4. 完成已确认范围内的实现、示例和自动维护文档。
5. 完成实际构建，逐项执行测试并持久化结果；修复后按影响范围重测。
6. 整理最终源码与平台程序，验证交付包和测试证据的对应关系。
7. 生成独立测试进度包，计算最终三包大小和 SHA256。
8. 保存交付文件，形成包含校验表和 RECORD 文件名的交付回答，并保存该回答的完整 RECORD。
9. 提供四项正式交付文件与 RECORD 下载链接。

本文件规定通用交付流程，不替代各版本功能范围的单独确认。
